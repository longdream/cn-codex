# CN-Codex / Codex Parity Audit

Date: 2026-06-09

## Completed in this pass

- Goal mode icon now uses `IconTargetArrow` in the composer and run summary.
- Goal mode run summaries now include per-turn token usage accounting. CN-Codex aggregates prompt, completion, and total tokens across all LLM iterations in a turn, stores that usage in the session JSONL metadata, returns it from `standalone_thread_read`, emits it in `turn-completed`, and renders total/input/output tokens in the run summary card.
- Goal mode now accepts Codex-style `/goal --tokens <budget> <objective>` input. Compact suffixes such as `98.5K` and `2M` are parsed into token budgets, sent to the backend, stored with the turn, returned in thread reads, emitted in `turn-completed`, and shown in the run summary. When the turn's total token usage reaches the requested budget, the run summary is marked budget-limited.
- Goal mode now has lightweight thread-level lifecycle state. Goal turns persist an objective/status/token budget/tokens-used record on the thread; `/goal` shows the current goal summary; `/goal pause`, `/goal resume`, `/goal clear`, and `/goal edit <objective>` update or clear that record without sending a model turn; bare `/goal edit` pre-fills the composer with the current objective; thread reads rehydrate the current goal into the UI; and cumulative goal token usage marks the thread goal as `budgetLimited`.
- Repository skills from `D:\rustwork\codex\.codex\skills` are present under `codey/skills`.
- The agent prompt now lists available local skills and tells the model to read the matching `SKILL.md` before using a skill.
- `tool_search` is now available as a function tool. It searches built-in tools, local `codey/skills`, plugin-bundled skills, plugin app connectors, and discovered direct MCP tools, returning callable tool specs, skill paths, app connector metadata, and trusted `codex-apps` connector IDs/names for the model to use next. The Responses adapter now also accepts official `tool_search_call` output items, routes client-side calls into the local `tool_search` executor, and serializes matching tool-search history back as `tool_search_call` / `tool_search_output` items when loadable tool specs are available.
- `tool_search` now emits a Responses-style `tools` array in addition to the human-readable `matches` list. MCP direct-tool search results are converted into deferred namespace tool specs and coalesced by namespace (for example, multiple `mcp__docs__*` results become one `mcp__docs` namespace with multiple function tools), and the Responses adapter preserves that loadable namespace output across history replay.
- `tool_search` ranking is now closer to Codex's BM25-backed search. CN-Codex builds a search document from each tool/skill/app entry, including function names, descriptions, usage text, metadata, paths, and JSON schema parameter names/descriptions/enums/variants, then ranks with a BM25-style score plus small exact-name boosts. This improves discovery for tools whose relevant terms live in parameter schemas rather than only in the top-level description.
- `apps_list` is now available as a function tool. It lists imported plugin app connectors, connector install URLs, plugin provenance, and currently exposed trusted `codex-apps` MCP tools for each connector.
- App connector prompt guidance now mirrors Codex's Apps instructions more closely. When local plugin app connectors exist, the system prompt explains explicit `[$app-name](app://{connector_id})` triggers, that apps map to MCP tools in the `codex-apps` server, that app tools may be visible already or lazy-loaded through `tool_search`, that `apps_list` can inspect installed connectors and exposed tools, and that app discovery should not use MCP resource/resource-template listing.
- `list_available_plugins_to_install` and `request_plugin_install` are now available as function tools. They let the agent list local Codex plugin cache candidates and import a selected plugin into `codey/plugins` by candidate id or unique name.
- `plugin_manage` is now available as a function tool for local workspace plugins. It lists, enables, disables, and uninstalls plugin bundles under `codey/plugins`; disabled plugins stay on disk but are excluded from skill prompts, MCP servers, app connectors, and hooks.
- `code_review` is now available as a function tool for local review flows. It reviews the current tracked git diff or a diff against a base ref, summarizes changed files and line counts, runs `git diff --check`, and flags obvious risks such as secret-looking additions, risky dynamic APIs, debug statements, new Rust panic paths, and source changes without matching tests.
- Shell execution is closer to Codex's current shell tool shape. The legacy `shell` tool now accepts both argv arrays and Codex-style command strings, and `shell_command` is available as a Codex-compatible alias with `workdir`, `timeout_ms`, `login`, `sandbox_permissions`, `justification`, `prefix_rule`, and `additional_permissions` fields. Per-command `require_escalated` / `with_additional_permissions` requests reuse the desktop command approval modal before execution.
- Lightweight unified exec sessions are now available:
  - `exec_command` starts a persistent command session, waits for `yield_time_ms`, and returns output plus a `session_id` when the process is still running.
  - `write_stdin` writes to a running exec session or polls recent output by `session_id`.
  - `close_exec_session` terminates and removes a running exec session by `session_id`, closing stdin and stopping the recorded process tree so long-running servers or stuck commands can be cleaned up explicitly.
  - Session output is incremental, so subsequent polls return new output instead of replaying the full buffer.
- Web tools are now real agent tools when `web_search` is enabled:
  - `web_search` returns current search result titles, snippets, and URLs.
  - `web_fetch` fetches a URL and extracts readable page text.
- Local memory tools are now available:
  - `memory_list` lists files under `codey/memories`, with optional cursor pagination and JSON output.
  - `memory_read` reads memory files with optional line windows, next-line offsets, and JSON output.
  - `memory_search` searches text memory files with optional cursor pagination, context lines, and JSON output.
  - `memory_write` creates, overwrites, or appends durable memories only when explicitly requested.
  - `memory_update` replaces exact text in existing durable memory files only when explicitly requested.
  - `memory_forget` deletes memory paths or removes matching memory lines only when explicitly requested.
- Generic MCP stdio tools are now available:
  - `mcp_list_servers` lists configured MCP servers without revealing env values.
  - `mcp_status` reports configured MCP servers without revealing env values and can probe tools, resources, resource templates, and prompts for availability/count diagnostics.
  - MCP stdio servers now reuse a persistent session inside the current `ToolExecutor` lifecycle instead of starting a fresh child process for every MCP request. CN-Codex keeps the initialized stdin/stdout JSON-RPC session per server, retries once after stale transport failures, clears sessions when the server configuration changes, and exposes session connection/request-count metadata in `mcp_status`.
  - MCP HTTP / Streamable HTTP-style server entries are now parsed from `codey/config.toml` and plugin `.mcp.json` / manifest MCP configs using `type = "http"` / `streamable-http` plus `url`. CN-Codex initializes HTTP MCP servers with JSON-RPC `initialize`, sends `notifications/initialized`, preserves `Mcp-Session-Id`, sends configured HTTP headers without exposing their values in status output, parses JSON and SSE `data:` responses, and routes the same `mcp_list_tools`, `mcp_call_tool`, resources, templates, prompts, direct-tool discovery, and `tool_search` paths through the HTTP transport.
  - `mcp_list_tools` lists tools from one or all enabled MCP servers.
  - `mcp_call_tool` calls a named MCP tool.
  - MCP discovery converts `tools/list` results into direct `mcp__server__tool` function tools with each tool's own input schema when MCP servers respond successfully, and reuses that direct-tool schema cache across turns while the MCP configuration is unchanged.
  - Direct MCP tool discovery preserves trusted `codex-apps` connector metadata (`connector_id`, `connector_name`, and connector description) for app-aware search, while ignoring connector metadata from untrusted custom MCP servers.
  - `mcp_list_resources` lists MCP resources.
  - `mcp_read_resource` reads a resource by URI.
  - `mcp_list_resource_templates` lists MCP resource templates.
  - `mcp_list_prompts` lists MCP prompts.
  - `mcp_get_prompt` resolves a prompt by name and optional arguments.
- `apply_patch` is available with official-style freeform support for Responses API providers and compatibility wrappers for other providers. In `wire_api = "responses"`, CN-Codex exposes `apply_patch` as a `custom` tool with the Codex Lark grammar and parses `custom_tool_call` / `response.custom_tool_call_input.delta` events. The executor accepts raw Codex patch bodies directly, plus compatibility wrappers via `{ "patch": "..." }` or `{ "command": "..." }`, supports add, update, delete, and simple move operations with relative-path safety checks, and emits `file-change-patch-updated` progress previews with structured changed-file actions for the tool card UI.
- `update_plan` is available as a function tool for multi-step agent work. It validates non-empty plan items, accepted statuses (`pending`, `in_progress`, `completed`), and the single `in_progress` invariant, then surfaces the plan in the tool card UI.
- `request_user_input` is available as a function tool for one to three structured questions when progress genuinely depends on the user. It emits a `server-request`, reuses the desktop approval modal interaction path, waits for the answer, and returns the response using the Codex-style `{ answers: { id: { answers: [...] } } }` shape.
- `request_permissions` is available as a function tool for requesting additional network or filesystem permissions. It emits a `server-request`, reuses the desktop approval modal path, waits for the user decision, returns a Codex-style response with `permissions`, `scope`, and `strict_auto_review`, and caches granted additional permission profiles so later `shell` / `shell_command` / `exec_command` calls with the same or narrower `with_additional_permissions` profile can proceed without a duplicate approval prompt.
- `view_image` is available as a function tool for local PNG, JPEG, GIF, and WebP files. It returns image format, dimensions, size, and absolute path; the frontend tool card previews local images through Tauri's asset URL.
- `image_generate` is available as a function tool for OpenAI Images API-compatible backends. It reads `CN_CODEX_IMAGE_API_KEY` or `OPENAI_API_KEY`, optionally uses `CN_CODEX_IMAGE_BASE_URL` and `CN_CODEX_IMAGE_MODEL`, supports `n` for multi-image generation, saves every returned image under `codey/images/generated` by default, and previews saved images in the tool card UI.
- A local Browser Skill is available at `codey/skills/browser/SKILL.md`, and the imported Browser plugin skill is adapted to CN-Codex's `browser_run` runtime rather than upstream Node REPL/browser-client bootstrap instructions. `browser_run` runs a real Playwright-controlled browser for navigation, UI interaction, rendered text extraction, screenshots, local web app testing, viewport changes, page snapshots, page HTML reads, page asset listing/bundling, common form controls, and basic tab/session actions (`list_tabs`, `new_tab`, `switch_tab`, `close_tab`). It opens or reuses the visible `cn-browser` Tauri WebView window through CDP first, then falls back to standalone Chromium if the visible browser endpoint is unavailable. Browser screenshots, asset bundles, and tab summaries are previewed in the tool card UI. Legacy browser-related skills such as `webapp-testing` and `browser-harness` now act as compatibility aliases that require the Browser Skill / `browser_run` path instead of launching separate Playwright or Chrome sessions.
- The desktop shell has a visible built-in browser entry in the sidebar. It opens or focuses a dedicated `cn-browser` Tauri WebView window, normalizes common addresses such as `localhost:1420`, persists its WebView data under `codey/browser/webview-data`, and keeps external pages outside the main window capability scope.
- Lightweight subagent tools are available:
  - `spawn_agent` starts a background internal subagent run and keeps it under the current workspace/runtime state.
  - `wait_agent` waits for one or more spawned subagents and returns their status/output.
  - `send_input` sends a follow-up message to a spawned subagent. CN-Codex records each submission in subagent input history and forwards it over the internal subagent channel when available.
  - `resume_agent` resumes a stopped spawned subagent by restarting the internal subagent engine with the same subagent id and task context.
  - `list_agents` lists spawned subagents by status.
  - `close_agent` closes a spawned subagent when it is no longer needed. For running internal subagents, CN-Codex sets a cancellation flag before marking the subagent closed.
  - Subagent records are persisted to `codey/subagents/state.json` and reloaded on startup. Records that were `running` when CN-Codex stopped are restored as `interrupted`, because their process handles cannot be recovered.
- Composer image attachments are now sent to models as multimodal inputs for OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, and native Gemini adapters. The persisted thread history keeps only text and attachment labels, avoiding large base64 session files.
- Vite no longer watches runtime state directories (`codey`, `logs`, `dist`, `src-tauri`), so session writes no longer reload the app.
- `dev.bat` checks port `1420`, kills the listening process when needed, then starts dev mode.
- Frameless window controls are wired through Tauri native APIs with Rust command fallbacks:
  - drag
  - minimize
  - maximize / restore
  - close
- `codey/plugins` now has a minimal local plugin loader:
  - discovers `.codex-plugin/plugin.json` and `.claude-plugin/plugin.json`
  - parses display metadata, manifest warnings, capability hints, and bundled skills
  - injects plugin-bundled skills into the agent skill prompt
  - merges plugin-bundled stdio/local MCP servers from `.mcp.json` or manifest `mcpServers`
  - discovers plugin app connectors from `.app.json` or manifest `apps` paths, shows them in Settings, and injects a bounded connector list into the agent prompt
  - exposes imported plugin app connectors through `apps_list`, including whether trusted `codex-apps` MCP tools are currently available for those connector IDs
  - exposes local Codex plugin cache candidates to the agent through `list_available_plugins_to_install`
  - imports a selected local Codex plugin cache candidate through `request_plugin_install`
  - lets Settings and the agent enable, disable, or uninstall local workspace plugins
  - runs lightweight project and plugin command hooks for `on-agent-start`, `on-user-prompt-submit`, `on-command-exec`, `on-file-change`, `on-agent-end`, `on-post-tool-use`, and `on-subagent-stop`
  - shows discovered plugins in the Settings integration panel
- Settings can import installed Codex plugin cache entries into the workspace `codey/plugins` directory through `plugin_import_codex_cache`. The current workspace has imported six local Codex plugin bundles:
  - `browser`
  - `computer-use`
  - `sites`
  - `documents`
  - `presentations`
  - `spreadsheets`
- Hooks runtime support now loads `codey/config.toml`, `codey/hooks.json`, plugin `hooks/hooks.json`, manifest hook paths, and inline manifest hook objects. It emits `hook-started` / `hook-completed` events and exposes the effective hook list in Settings.
- `UserPromptSubmit` is now a distinct hook event exposed as `on-user-prompt-submit`, separate from `on-agent-start`. CN-Codex runs it after a turn starts and before any model request. Hook output can block the prompt with legacy `decision:block`, exit code `2` stderr feedback, or `continue:false`; blocking feedback is saved as a visible assistant message and no model request is sent. Non-blocking `hookSpecificOutput.additionalContext` or plain stdout is injected as a system message for the same turn.
- `PreToolUse` / `on-command-exec` hooks now have actionable outcomes. CN-Codex parses Codex-style hook JSON output, including legacy `{ "decision": "block", "reason": "..." }`, `hookSpecificOutput.permissionDecision = "deny"` with a reason, exit code `2` with stderr feedback, and `permissionDecision = "allow"` with `updatedInput`. Blocking hooks now prevent the tool call from executing and return a tool result explaining which hook blocked it; `updatedInput` rewrites the tool arguments before execution. Invalid JSON-like hook output fails open but is marked as a failed hook run with `invalidOutput`.
- `PostToolUse` is now a distinct hook event exposed as `on-post-tool-use`, separate from the existing changed-files `on-file-change` hook. After a tool finishes, CN-Codex runs matching post-tool hooks and appends model-visible feedback for legacy block decisions, `hookSpecificOutput.additionalContext`, `continue: false` stop reasons, and exit code `2` stderr feedback. Invalid JSON-like output and unsupported `updatedMCPToolOutput` fail open with `invalidOutput` rather than corrupting the tool result.
- `Stop` hooks now have actionable continuation behavior. CN-Codex parses Stop hook `decision:block` results and exit code `2` stderr as continuation feedback, injects that feedback into the same turn as a model-visible `[Stop hook continuation]` system message, and lets the agent continue for another model iteration instead of ending immediately. `continue:false` / `stopReason` is treated as an explicit stop, and invalid JSON-like Stop output fails open with `invalidOutput`.
- `SubagentStop` hooks are now available as `on-subagent-stop` on the `close_agent` path. Hook declarations can use Codex-style `SubagentStop` / `subagent_stop`, match on the subagent role through `agentType` / `agent_type`, and return Stop-style block/continue output. CN-Codex appends model-visible `[SubagentStop hook feedback]` to the `close_agent` tool result so the parent agent can act on subagent lifecycle feedback.
