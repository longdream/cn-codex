# 测试报告生成

## 概述

测试报告是测试活动的最终交付物，向所有利益相关方传达质量状态。好的测试报告数据驱动、结论清晰、建议可行。

**核心原则：** 报告用数据说话，不用"基本正常"、"大致可以"等模糊表述。每个结论必须有数据支撑。

**宣告：** "我正在使用 test-report-generation 技能生成测试报告。"

## 何时使用

- 测试周期结束时
- 发版前质量评审
- 缺陷分析总结
- 测试进度汇报
- 项目复盘时的质量回顾

## 数据收集

在生成报告前，收集以下数据：

### 必须收集

| 数据项 | 来源命令 | 说明 |
|--------|---------|------|
| 单元测试结果 | `npm test -- --coverage` | 通过数/失败数/跳过数 |
| 代码覆盖率 | 同上（coverage报告） | 行/分支/函数覆盖率 |
| API 测试结果 | `npm test -- --testPathPattern=api` | 接口通过/失败 |
| E2E 测试结果 | `npx playwright test` | 场景通过/失败 |
| 性能测试数据 | `k6 run --out json=results.json` | 响应时间/吞吐量 |
| 安全扫描结果 | `npm audit --json` | 漏洞数量/级别 |
| 缺陷清单 | 测试过程中记录 | 严重级别/状态 |

### 覆盖率标准

| 指标 | 优秀 | 合格 | 不合格 |
|------|------|------|--------|
| 行覆盖率 | > 90% | > 70% | < 70% |
| 分支覆盖率 | > 85% | > 60% | < 60% |
| 函数覆盖率 | > 95% | > 80% | < 80% |
| 关键路径覆盖 | 100% | > 90% | < 90% |

## 报告生成流程

### 第1步：收集原始数据

```bash
# 运行测试并收集结果
cd server && npm test -- --coverage --json --outputFile=test-results.json
cd client && npm test -- --coverage --json --outputFile=test-results.json
npx playwright test --reporter=json > e2e-results.json
npm audit --json > audit-results.json
```

### 第2步：提取关键指标

从 JSON 输出中提取：
- 通过/失败/跳过数量
- 覆盖率百分比
- 失败用例详情
- 漏洞数量和级别

### 第3步：填充报告模板

使用收集的数据填充上述模板的每一个单元格。

**禁止：**
- 用 "N/A" 或 "待补充" 敷衍
- 没有执行的测试类型标记为 "未执行" 并说明原因
- 伪造或估算数据

### 第4步：撰写结论

基于数据做出质量评估：
- 通过率 > 95% 且无 P0 缺陷 → ✅ 可以发版
- 通过率 > 90% 且 P0 已修复 → ⚠️ 有条件发版
- 通过率 < 90% 或有未修复 P0 → ❌ 不建议发版

### 第5步：交付与存档

- 保存到 `docs/testing/测试报告.md`
- 同步更新测试用例执行状态
- 标记已发现缺陷到缺陷跟踪系统

## 质量度量仪表盘

长期追踪的度量指标：

| 指标 | 计算方式 | 健康标准 |
|------|---------|---------|
| 测试通过率 | 通过数/总数×100% | > 95% |
| 缺陷逃逸率 | 生产缺陷/总缺陷×100% | < 5% |
| 缺陷关闭周期 | 平均修复天数 | < 3天(P0)、< 7天(P1) |
| 测试覆盖率 | 工具报告值 | > 70% |
| 回归率 | 回归缺陷/修复数×100% | < 10% |
| 自动化率 | 自动化用例/总用例×100% | > 60% |

## 验证清单

报告生成后自检：
- [ ] 所有数据都来自实际执行结果（非估算）
- [ ] 每个测试层级都有结果记录
- [ ] 失败用例都有原因分析
- [ ] 缺陷都有严重级别和状态
- [ ] 性能数据包含具体数值（非"正常"）
- [ ] 安全扫描有具体漏洞数量
- [ ] 结论有明确的发版建议
- [ ] 改进建议可执行、有优先级
- [ ] 无模糊表述（"基本"、"大致"、"应该"）
