# 用户故事与功能建模

将需求描述拆解为标准用户故事和功能需求规格，产出可交付给开发团队的结构化文档。

<HARD-GATE>
必须基于已确认的需求采集文档（00-intake.md 或 01-boundary.md）进行建模。不得凭空编造用户角色或功能需求。如果上游文档不存在或不完整，要求先完成需求采集。
</HARD-GATE>

## 核心原则

- **每个故事足够小**：可在一个开发迭代内完成
- **验收标准必须可验证**：禁止模糊表述如"正常工作"、"用户体验好"
- **编号唯一且连续**：用户故事 US-xxx，功能需求 FR-xxx
- **YAGNI**：只建模明确需要的功能，不主动膨胀范围

## 建模流程

1. **读取上游文档** — 加载 `00-intake.md` 和 `01-boundary.md`
2. **识别用户角色** — 从需求中提取所有用户角色
3. **按角色拆解故事** — 每个核心功能拆为 1-N 个用户故事
4. **编写验收标准** — 每个故事至少 2 个可验证的验收条件
5. **提取功能需求** — 从故事中抽取系统级功能需求 FR-xxx
6. **标注非目标** — 从边界文档继承并补充 Non-Goals
7. **自审** — 检查覆盖性、一致性、可验证性
8. **用户确认** — 展示故事列表并征求确认

## 用户故事格式

```markdown
### US-{NNN}: {简短标题}

**描述**: 作为 {用户角色}，我希望 {功能描述}，以便 {业务价值}。

**优先级**: 必须 / 期望 / 可选

**验收标准**:
- [ ] {具体的、可验证的条件 1}
- [ ] {具体的、可验证的条件 2}
- [ ] {具体的、可验证的条件 3}

**关联需求**: F-{NNN} (来自 intake), FR-{NNN} (功能需求)
```

## 验收标准编写规则

**可验证 = 能用"是/否"回答是否满足**

| 类型 | 好的验收标准 | 坏的验收标准 |
|------|-------------|-------------|
| UI | 点击"提交"后显示成功提示，3 秒后自动关闭 | 提交后有反馈 |
| 数据 | 列表默认按创建时间倒序，每页显示 20 条 | 列表正常显示 |
| 权限 | 非管理员用户无法看到"删除"按钮 | 权限控制正确 |
| 性能 | 列表加载时间不超过 2 秒（100 条数据） | 性能可接受 |
| 错误 | 网络断开时显示"网络异常，请重试"提示 | 错误处理正常 |

## 功能需求格式

从用户故事中抽取系统层面的功能需求：

```markdown
- **FR-{NNN}**: {系统必须/应当} {具体功能描述}
  - 关联故事: US-{NNN}
  - 约束: {技术约束或业务规则}
```

功能需求的编写原则：
- 以"系统必须"或"系统应当"开头
- 一条需求只描述一个功能点
- 避免实现细节（不指定技术方案）
- 可以被独立测试

## 产出文档模板

保存到 `docs/prd-workspace/{feature}/02-stories.md`：

```markdown
# {Feature Name} — 用户故事与功能需求

## 用户角色

| 角色 | 描述 | 主要场景 |
|------|------|----------|
| {角色名} | {简要描述} | {典型使用场景} |

## 用户故事

### US-001: {标题}
**描述**: 作为 {角色}，我希望 {功能}，以便 {价值}。
**优先级**: 必须
**验收标准**:
- [ ] {条件 1}
- [ ] {条件 2}
**关联需求**: F-001, FR-001

### US-002: {标题}
...

## 功能需求

- **FR-001**: 系统必须 {功能描述}
  - 关联故事: US-001
  - 约束: {约束说明}

- **FR-002**: 系统必须 {功能描述}
  - 关联故事: US-002
  - 约束: {约束说明}

## 非目标 (Non-Goals)

- NG-001: {明确不做的功能}
- NG-002: {明确不做的功能}

## 覆盖矩阵

| intake 功能 (F-xxx) | 用户故事 (US-xxx) | 功能需求 (FR-xxx) | 状态 |
|---------------------|-------------------|-------------------|------|
| F-001 | US-001, US-002 | FR-001, FR-002 | 已覆盖 |
| F-002 | US-003 | FR-003 | 已覆盖 |
```

## 自审检查清单

建模完成后，逐项检查：

- [ ] 每个 intake 功能 (F-xxx) 都有对应的用户故事
- [ ] 每个用户故事都有至少 2 个可验证的验收标准
- [ ] 验收标准中没有模糊词汇（正常、合理、适当、良好）
- [ ] 功能需求编号连续，无遗漏
- [ ] 非目标清单完整，与 intake/boundary 文档一致
- [ ] 覆盖矩阵无空行（无遗漏功能）
- [ ] 用户角色与 intake 中的目标用户一致

## 常见错误

- **故事太大**: "作为用户，我希望有一个完整的订单管理系统" — 需要拆分为创建、查看、编辑、删除等独立故事
- **验收标准不可测**: "系统运行流畅" — 改为"页面加载时间 < 2s"
- **缺少边界场景**: 只写了正常流程，没有错误处理、空状态、权限不足等场景
- **自造需求**: 添加了 intake 中没有的功能 — 严格限定在已确认范围内
