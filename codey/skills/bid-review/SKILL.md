# 标书审查

## 前置条件
- 必须提供招标文件与标书文件。
- 缺少招标文件时必须报错：`请提供招标文件。`
- 执行前必须先在 `tender-document-parsing/.skill.env` 配置远程 `BID_API_BASE`（例如 `http://10.136.0.123:10104`）。
- 地址只允许远程服务，若命中 `localhost/127.0.0.1/0.0.0.0` 会被脚本直接拦截。
- 审查前必须先准备招标文件解析结果：
  - 常规场景：可复用已有解析结果；
  - **再次读取/重新读取/读取最新** 场景：必须重新调用解析并使用 `--force-refresh`，禁止继续使用旧产物。
- 语义门禁（强制）：
  - 仅当用户明确表达“重新读取/重刷/按最新文档重跑/重新解析”时，才允许使用 `--force-refresh`。
  - 若用户仅反馈“问题一样/结论一样/请继续分析”，不得自动触发强制重读，默认沿用当前可用内容继续审查。

## 对外输出要求（必须）
- 面向客户输出时，必须使用通俗中文业务表达，避免技术实现细节。
- 禁止在对客文本中出现以下内部术语或同类内容：
  - `query_route.json`、`review_preparation.json`、`source.md`、`chunks.json`、`artifact_dir`
  - `mode=chunks`、`mode=source`、`Grep`、`Read`、`chunk_0001`
  - `cache hit/miss`、`generated_at`、`token`、脚本绝对路径
- 可以在内部执行中使用上述信息，但对客回复必须做“业务化转述”：
  - 可说“已按章节逐条核对全文”，不要说“按 chunks 检索”
  - 可说“已重新读取并复核文档”，不要说“复用/命中某目录”
  - 可说“已定位到对应条款并完成交叉核验”，不要说具体中间文件名
- 若用户追问执行过程，可解释“已完成分段检索与证据复核”，仍不输出底层字段名和路径。
- 对客语言自检（强制）：
  - 不输出 JSON、代码块、命令行、文件绝对路径。
  - 不输出工具名和执行过程细节（例如“调用了某工具/某脚本”）。
  - 每条结论都要落在业务语言上：问题是什么、影响是什么、建议怎么改。
  - 定位信息禁止出现 `P\d+`、`(P\d+)`、`第X页` 等页码样式；仅允许章节名或“章节未定位”。

## 审查流程（三步）

### Step 1：获取招标文件结构化要求

调用招标文件解析技能脚本获取 key_info：

```bash
python scripts/call_extract.py --file "ABSOLUTE_TENDER_FILE_PATH"
```

当用户要求“按最新文档重读”时，必须改为：
```bash
python scripts/call_extract.py --file "ABSOLUTE_TENDER_FILE_PATH" --force-refresh
```

若用户未明确提出“重读/重刷”语义，则保持常规命令，不加 `--force-refresh`。

从返回的 JSON 中提取 `data.categories` 数组，每个条目包含：
- `category`：分类名（废标项/企业资质要求/评分标准/...）
- `items`：条目列表，每条含 `content`（条款原文）

### Step 2：逐类别审查（按检索入口建议执行两级召回）

对每个审查类别，按以下优先级从标书中召回相关片段：

> 说明：本节属于内部执行流程，禁止将字段名、文件名、路径名原样输出给客户。

#### 第零步：先读取检索路线文件（强制）

1. 先读取 `review_preparation.json` 中以下字段：
   - `bid_query_route_file`
   - `bid_query_route`（若存在）
2. 再读取 `bid_query_route_file`（即 `query_route.json`），至少确认：
   - `mode`（`source` 或 `chunks`）
   - `source_char_count`
   - `threshold`
   - `source_md_path`
   - `chunks_json_path`
2. 执行规则：
   - 当 `mode == "chunks"`（通常 `source_char_count > threshold`）时：**第一级必须从 `chunks/*.md` + `chunks.json` 开始检索**
   - 当 `mode == "source"` 时：第一级在 `source.md` 中检索，可直接读取全文上下文，不需要回跳 `chunks.json`
3. 禁止事项：`mode == "chunks"` 场景下，禁止直接只扫 `source.md` 后给结论。

#### 第一级：关键词 Grep 搜索（按 route 选择入口，最多两轮换词）

1. Round1（初始关键词）：
   - 从 key_info 条目的 `content` 中提取 2~5 个核心关键词（去掉常见虚词：的/了/和/在/是/等/应/须/为）
   - `mode == "chunks"`：在 `bid_artifact_dir/chunks/*.md` 与 `bid_artifact_dir/chunks.json` 中 Grep
   - `mode == "source"`：在 `bid_artifact_dir/source.md` 中 Grep
2. 若 Round1 无命中，执行 Round2（LLM换词）：
   - 基于当前条款内容，让 LLM 重写一组替代关键词（同义词/缩写/业务别称）
   - 用替代关键词再执行同范围 Grep（`chunks` 或 `source`）
3. 若 Round2 仍无命中：标记“关键词检索两轮未命中”，进入第二级章节定位回退，不得直接终止。
4. 任一轮命中后，执行**多命中点证据采集**：
   - **最少命中数**：单条审查项至少读取 3 处命中位置（优先来自不同 chunk / http不同小节），如果命中不足 3 处则全部读取。
   - **每处读取范围**：用 Read 工具读取命中行前后各 20 行（共约 40 行）作为该命中点的上下文片段。
   - **模板/引用过滤**：若已读取的命中点中，超过半数为模板占位（如"XXX公司""详见附件""另行提供"等引用性语句）且无实质内容，必须继续追加读取后续命中位置，直到获得可判定的实质证据或命中点全部耗尽。
   - **证据不足处理**：所有命中点读取完毕后仍无实质证据，不得强行判定，标记"证据不足"进入第二级回退。
   - 仅靠命中行本身不足以做审查判断，必须结合上下文理解该关键词出现语境。

#### 第二级：章节定位 + 按行召回（两轮关键词检索未命中时触发）
http
1. 根据审查类别/条目内容，在标书中动态查找相关章节标题（用 Grep 搜索章节名关键词）
2. 定位到目标章节后，用 **Read** 工具按行读取该章节内容，每次读取 100 行
3. **最少读取要求**：进入章节回退后，至少连续读取 2 批（共 200 行）后才允许做出结论判断。即使第一批 100 行看似无关，也必须继续读取第二批。
4. 若 200 行后仍无法判断，继续按 100 行递进读取，直至章节结束。
5. **禁止强判**：章节读完后仍无法找到实质证据，必须输出"证据不足/待补充"，不得凭推测或缺失即判定为问题。

#### 组装审查 prompt

将以下内容组装为审查判断的输入：
- 招标要求原文（来自 key_info 条目 content）
- 标书召回片段（来自 Grep 命中 或 章节按行召回）
- 审查指令（见下方各类别细则）

然后自行调用 LLM 做判断，产出结构化 issues。

#### 强制性语义判断规则（所有类别均适用）

1. **引用/转述排除规则**：若命中片段中关键词仅出现在"详见/参见/见附件/另行提交/单独提交/不得出现在"等引用性、指示性表述中，且上下文无实质违规内容（无具体数据/表格/金额/实际敏感内容），则**不构成违规，不得报错**。例如：
   - "详见附件：报价表" → 仅引用指向，不代表本文件包含报价表内容
   - "报价文件须单独提交" → 这是招标要求的转述，不是违规行为

2. **实质内容判定标准**：只有在命中行周围 40 行上下文中确实包含了违规的实质内容（如实际报价金额数字/敏感词直接表述/完整表格数据），才可判定为问题

3. **必须引用完整上下文**：输出问题时必须附带命中行周围的关键上下文原文（至少 3~5 行），让用户可直接验证判断依据

4. **禁止仅凭关键词命中报错**：绝不能因为搜索到某个关键词就直接判定为问题，必须理解该关键词在上下文中的实际语义后才能做出判断

### 输出前证据自检门禁（强制执行）

在输出任何问题之前，对每条待输出的 issue 逐一核对以下清单：

1. **双侧证据要求**：每个问题必须同时具备招标证据（条款原文）+ 标书证据（至少一段实质内容）。
   - 若标书证据仅为引用/目录/模板片段（如"详见附件""XXX""待定"），**不满足实质证据标准**。
2. **实质内容最低标准**：标书证据中必须包含以下至少一种实质内容才可判定为"高风险"或"中等风险"：
   - 具体数据/金额/日期/参数
   - 明确的承诺或声明
   - 实际的技术方案/配置/人员信息
   - 或：明确的缺失（在相关章节中确实找不到对应内容的证据）
3. **不满足则降级或排除**：
   - 仅有模板/引用/目录片段 → 不得输出为"高风险"或"中等风险"，只能标注为"低风险"或直接排除
   - 无法找到任何实质标书证据 → 输出为"证据不足/待补充"，不得强行定性

### Step 3：输出结论

按 6 个类别汇总输出，每个问题项必须包含（全部使用中文标签）：
- `审查类别`：如“响应审查/商务条款”
- `风险等级`：高风险 / 中等风险 / 低风险
- `问题描述`：问题是什么，为什么会影响评审
- `整改建议`：可执行的修正动作
- `招标依据`：招标文件证据（章节名 + 原文片段）
- `标书依据`：标书证据（章节名 + 原文片段）
- `结论状态`：已确认问题 / 证据不足待补充
- 对客展示时必须转成自然语言，不输出中间产物字段或检索技术术语。
- **严禁输出英文标签/键名**：例如 `description`、`suggestion`、`tender_evidence`、`bid_evidence`、`severity`、`category`。

## 审查维度与判断指令

### 1) 废标项审查

**数据来源**：key_info 中 `category == "废标项"` 的所有条目

**审查指令**：
- 对每条废标条款，判断投标文件是否已实质性满足该要求
- **只有投标人确实未响应、缺失必要证据材料、或明确违反的才报"高风险"**
- 招标文件中的流程说明、注意事项、平台操作指引不算废标项
- "是否满足"的判断标准：标书中能找到对应的承诺/证明/材料/声明
- 风险等级固定为 `高风险`

### 2) 响应审查

**数据来源**：key_info 中以下 category 的条目：
- 企业资质要求
- 人员资质要求
- 技术参数要求
- 商务条款
- 标书结构要求
- 密封要求

**审查指令**：
- 只审查实质性条款（投标人必须在标书中体现的具体要求）
- 排除流程说明/投标须知/定义/法律条文/评标程序等非响应性内容
- 对每条要求判断响应状态：
  - `已响应`：标书中有明确对应内容
  - `响应不充分`：有提及但不完整或缺少证据
  - `未响应`：标书中找不到对应内容
- 风险等级：未响应 → `高风险`，响应不充分 → `中等风险`
- 响应率公式：`（已响应 + 响应不充分）/ 实质性条款总数 * 100%`

### 3) 一致性审查

**数据来源**：在标书中搜索以下关键词的所有出现位置：
- 项目经理、法定代表人、联系人、授权代表
- 报价金额、总价、单价
- 工期、交付时间、有效期
- 配置参数、技术指标、规格型号

**审查指令**：
- 检查**同一角色/同一参数**在标书不同位置是否一致
- 不同角色允许有不同姓名（项目经理≠法定代表人，这是正常的）
- 同一角色在不同页面出现不同姓名才报错
- 风险等级：
  - 报价/配置/工期/人员信息不一致 → `高风险`
  - 技术参数不一致 → `中等风险`
  - 其他非核心不一致 → `低风险`

### 4) 模拟评分

**数据来源**：key_info 中 `category == "评分标准"` 的条目

**审查指令**：
- 根据评分标准逐项在标书中查找对应内容并模拟打分
- 每个评分项需输出：评分项名称、满分值、模拟得分、扣分原因
- 输出低分项与扣分原因，并给出提分建议
- 提分建议按"投入产出比"排序：优先高权重、易整改、提分快条目
- 风险等级固定为 `中等风险`
- 必须附加免责声明：`模拟评分仅为 AI 参考值，最终得分以评标委员会评审为准`

### 5) 基础审查

**数据来源**：对标书全文进行格式/规范性检查

**审查指令**：
- 检查项：错别字/占位符（如"XXX公司"）、标点错误、金额单位不一致、日期过期、字体格式不统一、页码错误、签章位置缺失
- 风险等级：
  - 过期日期、敏感词命中 → `中等风险`
  - 其他格式问题 → `低风险`

### 6) AI 补充

**审查指令**：
- 基于全部审查上下文，补充其他重要风险项
- 必须给出明确问题描述与建议
- 风险等级根据实际风险判断

## 输出格式

### 对客表达模板（强制）

对客户的最终回复统一按以下顺序组织，且全部使用通俗中文：

1. **结论总览**：高风险/中等风险/低风险分别多少项，是否存在“证据不足待补充”。  
2. **问题清单**：每项包含“问题-影响-建议”，并标明对应章节名称（不用技术字段名）。  
3. **已核验通过项**：列出已确认满足要求的关键点，避免只报问题不报通过项。  
4. **待补材料清单**：明确还缺哪些文件或证据，补齐后可复核哪些结论。

### 对客字段命名门禁（强制）

- 对客文本中，字段名必须是中文：如“问题描述、整改建议、招标依据、标书依据、风险等级、结论状态”。
- 不允许出现任何英文键名或中英混排标签（例如 `description:`、`suggestion:`、`bid_evidence:`）。
- 若为列表展示，也必须使用中文前缀（例如“问题描述：…”，“整改建议：…”），不得使用英文冒号键名格式。

### 定位输出规则

引用证据时统一使用 **「章节名 + 证据原文片段」** 定位，不使用页码或行号。

- 引用格式：`标书【章节名】：证据原文片段`
- 章节名取自 source.md 中的 `#`/`##` 标题或 chunks.json 中的 `chapter`/`section` 字段
- 如果文档未分章（章节为"全文"），直接引用证据原文即可
- 若证据片段中仅出现目录页码索引（如 `（P2200）`、`......2200`），视为无效定位，必须改为“章节未定位”或补充真实章节证据
- 严禁输出 `标书P18`、`P2200`、`第220页` 等任何页码式定位表达

正确示例：`标书【合同条款】：履约保证金金额：合同金额的 / %（为空）`
正确示例：`标书【商务偏离表】：本投标人承诺无负偏离`
错误示例：`标书P18：...`（不使用页码定位）

### 输出结构

输出可灵活组织，但必须包含以下结构：

```
"【项目名称】"标书审查结论

基础审查：正常/有问题（N项）
废标项审查：正常/有问题（N项，高风险）
一致性审查：正常/有问题（N项）
响应审查：响应率 XX%（已响应N/响应不充分N/未响应N）
模拟评分：预估得分 XX/100

---
问题清单（按风险等级排序）：
[高风险] 废标项审查：问题描述... 招标【评标办法】，标书【合同条款】。建议：xxx
[中等风险] 响应审查：问题描述... 招标【投标人须知】，标书【商务偏离表】。建议：xxx
[低风险] 基础审查：问题描述... 标书【投标函】。建议：xxx
```

## 风险等级解释
- `高风险`：招标文件明确要求项、废标项/一票否决项、违法内容等致命风险
- `中等风险`：不致命但会影响得分或合规性的问题
- `低风险`：对投标结果影响较小的规范性问题

## 执行方式

本技能不再调用后端审查 API。Agent 直接按上述流程自主完成审查。
其中 ask-ai 已改为策略文本提示：本地脚本只输出 `ask_ai_strategy_text`，由 Cowork 自主发起问询，不在本地新增 LLM 调用。

### 远程服务地址配置（强制）
- `call_review.py` 内部复用 `tender-document-parsing/scripts/local_pipeline.py` 的地址解析逻辑。
- 因此统一在 `tender-document-parsing/.skill.env` 维护 `BID_API_BASE`，`bid-review` 无需重复维护同名配置。
- 若需单次临时覆盖，可在命令后追加 `--api-base "http://10.136.0.123:10104"`。

### Bash/Shell 超时配置（强制）
- 本 Skill 中所有 `python scripts/*.py` 命令都必须通过 Bash/Shell 工具执行。
- 执行时必须显式设置：`block_until_ms: 3600000`（1 小时）。
- 该规则覆盖本节全部 Python 执行场景（常规执行与 `--force-refresh` 等变体）。
- 禁止省略该参数或使用默认超时，避免长时审查任务在工具层被提前中断。

### 产物目录结构

每个 artifact_dir 内：
- `source.md` — 文档全文 markdown（用于 Grep 搜索）
- `chunks/` — 分块 markdown 文件（按章节/段落切分）
- `chunks.json` — 分块 JSON（含 chapter/section 章节信息）

### Agent 自主审查流程

1. 调用预处理脚本（见上方"预处理"），它会自动：
   - 调用 `tender-document-parsing` 技能解析招标文件，得到 key_info（废标项/资质要求/评分标准等分类条目）
   - 解析标书文件，生成 source.md 文本产物（干净文本，按章节以 `#`/`##` 标题分隔）
2. 读取 `review_preparation.json` 中 `bid_query_route_file`，并读取该文件得到 `mode`
3. 从 `key_info.result.categories` 按审查类别分组，每个条目的 `content` 是招标文件中的条款原文
4. 对每个类别的每个条目：
   - 从招标条款 `content` 中提取 2~5 个核心关键词
   - **第一级**：按 `mode` 检索（最多两轮：初始关键词 + LLM替代关键词）
   - **第二级**（两轮无结果时）：搜索章节标题 → Read 该章节（每次 100 行）
5. 用召回的标书片段 + 招标要求原文组装 prompt，调 LLM 判断
6. 汇总所有类别结论，按风险等级排序输出
