# 测试用例设计

## 概述

测试用例是测试执行的基本单元。好的测试用例能以最少的数量覆盖最多的场景，发现最多的缺陷。本技能提供系统化的测试用例设计方法，确保测试覆盖全面且高效。

**核心原则：** 测试用例设计是一门科学，不是随机想到什么测什么。

**宣告：** "我正在使用 test-case-design 技能设计测试用例。"

## 何时使用

- 为新功能设计测试用例
- 为已有功能补充测试覆盖
- 为 bug 修复设计回归测试用例
- 进行探索性测试前的结构化设计
- 需要评审测试覆盖完整性时

## 测试用例结构

每个测试用例必须包含：

```markdown
| 字段 | 说明 |
|------|------|
| TC-ID | 唯一标识符，格式: TC-[模块]-[序号] |
| 标题 | 一句话描述测试目标 |
| 前置条件 | 执行前需满足的状态/数据 |
| 测试步骤 | 具体操作步骤（编号列表） |
| 预期结果 | 每步对应的期望输出 |
| 优先级 | P0(阻塞)/P1(核心)/P2(常规)/P3(低) |
| 测试类型 | 功能/边界/异常/性能/安全 |
```

## 设计技术

### 1. 等价类划分（Equivalence Partitioning）

将输入数据划分为若干等价类，从每个类中选取代表值。

**原则：** 同一等价类中的任何值，系统行为相同。

**示例 — 年龄验证（18-65岁有效）：**
| 等价类 | 取值范围 | 代表值 | 预期 |
|--------|---------|--------|------|
| 有效类 | 18-65 | 30 | 通过 |
| 无效类-过小 | < 18 | 10 | 拒绝 |
| 无效类-过大 | > 65 | 80 | 拒绝 |
| 无效类-非数字 | 字母/符号 | "abc" | 错误提示 |
| 无效类-空值 | null/undefined | "" | 错误提示 |

### 2. 边界值分析（Boundary Value Analysis）

在等价类边界处取值，边界处最容易出错。

**取值规则：** 边界值、边界值-1、边界值+1

**示例 — 年龄验证（18-65岁有效）：**
| 测试值 | 位置 | 预期 |
|--------|------|------|
| 17 | 下界-1 | 拒绝 |
| 18 | 下界 | 通过 |
| 19 | 下界+1 | 通过 |
| 64 | 上界-1 | 通过 |
| 65 | 上界 | 通过 |
| 66 | 上界+1 | 拒绝 |

### 3. 决策表（Decision Table）

处理多条件组合的复杂业务逻辑。

**示例 — 订单折扣规则：**
| 条件 | R1 | R2 | R3 | R4 |
|------|----|----|----|----|
| VIP会员 | Y | Y | N | N |
| 订单>500元 | Y | N | Y | N |
| **动作** | | | | |
| 折扣20% | X | | | |
| 折扣10% | | X | X | |
| 无折扣 | | | | X |

### 4. 状态转换（State Transition）

适用于有明确状态流转的功能。

**示例 — 订单状态：**
```
[待支付] --支付成功--> [已支付] --发货--> [已发货] --签收--> [已完成]
    |                     |                  |
    |--超时取消-->       |--退款-->        |--拒收-->
    [已取消]            [已退款]          [退货中]
```

**测试用例覆盖：**
- 所有有效转换路径
- 所有无效转换尝试（如：已取消 → 已发货）
- 转换条件（超时时间、权限等）

### 5. 场景法（Scenario-Based）

从用户视角描述完整业务场景。

**基本流（Happy Path）：**
```
用户登录 → 浏览商品 → 加入购物车 → 结算 → 支付 → 完成
```

**备选流（Alternative Flows）：**
```
- 登录失败 → 重试 → 锁定
- 库存不足 → 提示 → 移除
- 支付失败 → 重试 → 取消订单
```

**异常流（Exception Flows）：**
```
- 网络中断 → 数据恢复
- 并发操作 → 数据一致性
- 会话超时 → 重新认证
```

## 测试用例模板

产出文件：`docs/testing/测试用例.md`

```markdown
# [功能名] 测试用例

## 概述
- 功能描述：[一段话]
- 设计方法：[使用了哪些设计技术]
- 用例总数：[X] 个（P0: x, P1: x, P2: x, P3: x）

## 测试用例清单

### TC-LOGIN-001: 正确凭据登录成功
- **优先级：** P0
- **类型：** 功能-正向
- **前置条件：** 已注册用户 test@example.com / password123
- **步骤：**
  1. 打开登录页面
  2. 输入邮箱 test@example.com
  3. 输入密码 password123
  4. 点击"登录"按钮
- **预期结果：**
  1. 页面跳转到首页
  2. 显示用户名
  3. 返回 JWT token
  4. HTTP 状态码 200

### TC-LOGIN-002: 错误密码登录失败
- **优先级：** P0
- **类型：** 功能-反向
- **前置条件：** 已注册用户 test@example.com
- **步骤：**
  1. 打开登录页面
  2. 输入邮箱 test@example.com
  3. 输入错误密码 wrongpass
  4. 点击"登录"按钮
- **预期结果：**
  1. 停留在登录页面
  2. 显示错误提示"邮箱或密码错误"
  3. HTTP 状态码 401
```

## 覆盖率检查

用例设计完成后，验证覆盖率：

- [ ] 所有等价类（有效+无效）都有至少一个用例
- [ ] 所有边界值都已覆盖
- [ ] 所有业务规则组合都有对应决策表行
- [ ] 所有状态转换（有效+无效）都已覆盖
- [ ] 基本流、备选流、异常流都有场景
- [ ] P0 功能有正向和反向用例
- [ ] 错误处理和边缘情况已考虑
- [ ] 并发/竞态条件已考虑（如适用）

## 用例编写原则

1. **一个用例测一件事** — 不要在一个用例里验证多个独立行为
2. **独立可执行** — 每个用例不依赖其他用例的执行结果
3. **可重复** — 任何人任何时候执行，结果一致
4. **预期明确** — "系统正常工作" 不是有效的预期结果
5. **步骤具体** — "输入数据" 不够，要写明输入什么数据
6. **优先级合理** — P0 只给核心路径，不要所有用例都是 P0

## 自动化转化指南

设计好的用例应能直接转化为自动化测试代码：

```typescript
// TC-LOGIN-001 → 自动化代码
describe('登录功能', () => {
  test('正确凭据登录成功', async () => {
    const response = await request(app)
      .post('/api/auth/login')
      .send({ email: 'test@example.com', password: 'password123' });

    expect(response.status).toBe(200);
    expect(response.body.token).toBeDefined();
    expect(response.body.user.email).toBe('test@example.com');
  });

  test('错误密码登录失败', async () => {
    const response = await request(app)
      .post('/api/auth/login')
      .send({ email: 'test@example.com', password: 'wrongpass' });

    expect(response.status).toBe(401);
    expect(response.body.message).toContain('邮箱或密码错误');
  });
});
```
