# 测试策略制定

## 概述

在编写任何测试代码之前，必须先制定测试策略。测试策略是测试活动的顶层设计文档，决定测什么、不测什么、用什么方式测、优先级如何排列。

**核心原则：** 没有策略的测试是盲目的，盲目的测试浪费时间且给人虚假的安全感。

**宣告：** "我正在使用 test-strategy-planning 技能制定测试策略。"

## 何时使用

- 接手新项目的测试任务
- 新功能上线前的测试规划
- 重大重构后的回归测试规划
- 发现严重缺陷后的补充测试规划
- 定期测试策略复审

## 测试金字塔（分层策略）

```
        /  E2E  \           少量 - 验证关键用户流程
       /  集成测试  \        中量 - 验证模块协作
      /   单元测试    \      大量 - 验证核心逻辑
     / 静态分析 + Lint  \    自动 - 类型检查、代码规范
```

**分层比例建议：**
| 层级 | 占比 | 执行频率 | 执行时间 |
|------|------|---------|---------|
| 静态分析 | 自动 | 每次保存 | < 1s |
| 单元测试 | 70% | 每次提交 | < 30s |
| 集成测试 | 20% | 每次 PR | < 5min |
| E2E 测试 | 10% | 每日/发版前 | < 30min |

## 策略制定流程

### 第1步：需求与风险分析

**输入：** 需求文档、代码库、架构文档

**分析维度：**
1. **功能风险** — 哪些功能最核心？故障影响最大？
2. **技术风险** — 哪些模块最复杂？依赖最多？变更最频繁？
3. **业务风险** — 哪些场景涉及资金、隐私、合规？
4. **历史风险** — 哪些区域历史缺陷最多？

**风险矩阵模板：**
```markdown
| 模块/功能 | 影响程度(1-5) | 出错概率(1-5) | 风险分(影响×概率) | 测试优先级 |
|-----------|-------------|-------------|-----------------|-----------|
| 支付流程   | 5           | 3           | 15              | P0 - 必测  |
| 用户登录   | 4           | 2           | 8               | P1 - 重点  |
| 个人设置   | 2           | 2           | 4               | P2 - 常规  |
```

### 第2步：确定测试类型

根据风险分析结果，选择适用的测试类型：

**测试类型选择矩阵：**
| 测试类型 | 适用场景 | 工具推荐 |
|---------|---------|---------|
| 单元测试 | 纯函数、业务逻辑、工具类 | Jest / Vitest / pytest |
| 组件测试 | React/Vue 组件渲染与交互 | Testing Library + Vitest |
| API 测试 | REST/GraphQL 接口验证 | Supertest / httpx / Postman |
| 集成测试 | 模块间协作、数据库交互 | Jest + 真实DB / Testcontainers |
| E2E 测试 | 关键用户流程端到端 | Playwright / Cypress |
| 性能测试 | 高并发、响应时间要求 | k6 / Artillery / autocannon |
| 安全测试 | OWASP Top 10、依赖漏洞 | npm audit / OWASP ZAP / Snyk |
| 可访问性测试 | 无障碍合规 | axe-core / Lighthouse |
| 兼容性测试 | 多浏览器/多设备 | Playwright multi-browser |

### 第3步：定义测试范围

**必须明确：**
- **测试范围内（In Scope）：** 列出要测试的模块和场景
- **测试范围外（Out of Scope）：** 列出不测的内容及原因
- **测试入口标准：** 何时开始测试（代码冻结、构建通过等）
- **测试出口标准：** 何时结束测试（覆盖率、通过率、无 P0 缺陷等）

### 第4步：工具链选型

根据项目技术栈确定工具组合：

**Node.js/TypeScript 项目：**
```
单元/组件: Vitest + @testing-library/react
API: Supertest
E2E: Playwright
覆盖率: c8 / istanbul
性能: k6 / autocannon
安全: npm audit + Snyk
```

**Python 项目：**
```
单元: pytest + pytest-cov
API: httpx / requests + pytest
E2E: Playwright (Python)
覆盖率: coverage.py
性能: locust / k6
安全: pip-audit + bandit
```

### 第5步：制定执行计划

**CI/CD 分级执行策略：**
```
每次 Commit → 静态分析 + 单元测试（< 30s）
每次 PR     → + 集成测试 + API 测试（< 5min）
每日构建    → + E2E 测试 + 回归测试（< 30min）
发版前      → + 性能测试 + 安全扫描 + 全量回归（< 2h）
```

## 验证清单

- [ ] 风险矩阵覆盖所有核心模块
- [ ] 测试类型选择有据可依
- [ ] 范围边界清晰（In/Out Scope）
- [ ] 工具链与项目技术栈匹配
- [ ] CI/CD 分级策略可落地
- [ ] 入口/出口标准可量化
- [ ] 无遗漏的高风险区域
